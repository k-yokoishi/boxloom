Every operation below is available through the boxloom Python SDK. The same operations are documented for the [REST API](./rest).

These examples use the connection configured during [Installation](../installation).

## Conventions

Top-level functions share one process-wide client. Call `boxloom.init()` to configure it explicitly, or let the first call configure it from `BOXLOOM_BASE_URL`, `BOXLOOM_AUTH_TOKEN`, and `BOXLOOM_TIMEOUT_SECONDS`.

Dimensions, blocks, and entities are named with namespaced IDs such as `minecraft:overworld`, `minecraft:stone`, and `minecraft:arrow`. A dimension must be loaded by the running server; a block or entity ID must exist in the server's registries. Operations that act on the world take `dimension` as a keyword argument defaulting to `minecraft:overworld`.

Block coordinates are `int` and must fit in 32 bits. Player and entity coordinates are `float` and must be finite. Every result is a frozen dataclass, so its attributes are read-only.

Every operation runs on the Minecraft server thread, so a stalled server surfaces as a timeout rather than a hang.

## Errors

Every failure raises a subclass of `boxloom.BoxloomError`.

| Exception | Raised when |
| --- | --- |
| `ApiError` | The server returned an error response. Carries `status`, `code`, and `message`. |
| `ConnectionError` | The boxloom server could not be reached. |
| `ProtocolError` | The response did not match the API contract. |
| `ConfigurationError` | The connection configuration is missing or invalid. |
| `EventCursorExpiredError` | An event stream cursor can no longer be resumed. Subclass of `ApiError`. |
| `EventStreamError` | The server reported a failure after the event stream was open. |

```python
from boxloom import ApiError, set_block

try:
    set_block(0, 100, 0, "minecraft:not_a_block")
except ApiError as error:
    print(error.status, error.code, error.message)
```

`ApiError.status` and `ApiError.code` carry the HTTP status and machine-readable code from the server. These can come from any operation; codes specific to one operation are listed with that operation.

## `summon`

<Operation id="summon">

```python
summon(
    entity: str,
    x: float,
    y: float,
    z: float,
    *,
    nbt: Optional[Dict[str, Any]] = None,
    dimension: str = "minecraft:overworld",
) -> SummonResult
```

**Parameters**

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `entity` | `str` | required | Namespaced ID of a registered, summonable entity type. |
| `x`, `y`, `z` | `float` | required | Spawn position. Finite, and inside Minecraft's spawnable bounds. |
| `nbt` | `Optional[Dict[str, Any]]` | `None` | Entity NBT, nested at most 128 levels deep. The `id` key is always overwritten with `entity`. |
| `dimension` | `str` | `"minecraft:overworld"` | Namespaced ID of a loaded dimension. |

`nbt` values convert as follows: `int` becomes an int tag, or a long tag when outside the 32-bit range; `float` becomes a double tag; `bool` becomes a byte tag; `str` becomes a string tag; `dict` and `list` nest. `None` is rejected.

**Returns** — `SummonResult`

| Attribute | Type | Description |
| --- | --- | --- |
| `uuid` | `str` | UUID of the summoned entity. |
| `entity` | `str` | Resolved namespaced entity type ID. |
| `dimension` | `str` | Resolved namespaced dimension ID. |
| `x`, `y`, `z` | `float` | Position of the entity after spawning. |

**Example**

```python
from boxloom import summon

entity = summon(
    "minecraft:arrow",
    0,
    100,
    0,
    nbt={"Motion": [0.0, -1.5, 0.0]},
)
print(entity.uuid)
```

</Operation>

## `set_time`

<Operation id="set_time">

```python
set_time(
    time: Union[int, str],
    *,
    clock: str = "minecraft:overworld",
) -> TimeResult
```

**Parameters**

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `time` | `int` or `str` | required | Absolute total ticks from `0` to `2147483647`, or a time marker ID such as `"day"`. An omitted namespace resolves to `minecraft`. |
| `clock` | `str` | `"minecraft:overworld"` | Registered world clock ID. |

**Returns** — `TimeResult`

| Attribute | Type | Description |
| --- | --- | --- |
| `clock` | `str` | Resolved namespaced world clock ID. |
| `ticks` | `int` | Total elapsed ticks immediately after setting the clock. |

**Example**

```python
from boxloom import set_time

set_time("day")       # Equivalent to /time set day.
set_time("night")
result = set_time(6000)
print(result.ticks)    # 6000
```

For the vanilla Overworld, markers occur at `1000` (`day`), `6000` (`noon`),
`13000` (`night`), and `18000` (`midnight`) within each 24,000-tick day. If the
clock is at `14000`, `set_time("day")` advances it to `25000`.
`set_time(1000)` instead resets its total ticks to `1000`.

</Operation>

## `watch_event`

<Operation id="watch_event">

```python
EventType = Literal["chat.message", "player.death"]
Event = Union[ChatEvent, PlayerDeathEvent]

watch_event(
    event_type: Optional[EventType] = None,
    *,
    last_event_id: Optional[str] = None,
    reconnect: bool = True,
) -> EventStream[Event]
```

**Parameters**

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `event_type` | `Optional[EventType]` | `None` | Receive all supported event types, or filter to `"chat.message"` or `"player.death"`. Unknown values raise `ValueError`. |
| `last_event_id` | `Optional[str]` | `None` | Resume strictly after this event ID. `None` starts at the live position when iteration first opens the connection. |
| `reconnect` | `bool` | `True` | Reconnect automatically using the last received cursor after a connection drops. |

**Returns** — `EventStream[Event]`, an iterator and context manager with `last_event_id` and `close()`.

The stream yields `ChatEvent` and `PlayerDeathEvent`. Both carry:

| Attribute | Type | Description |
| --- | --- | --- |
| `type` | `EventType` | Fixed discriminator: `"chat.message"` or `"player.death"`. |
| `id` | `str` | Opaque event ID, usable as `last_event_id`. |
| `timestamp` | `str` | UTC ISO-8601 instant. |
| `player` | `Player` | The player, with `username` and `uuid`. |
| `message` | `str` | The chat text or Minecraft's plain-text death message. |

`PlayerDeathEvent` also carries:

| Attribute | Type | Description |
| --- | --- | --- |
| `dimension` | `str` | Namespaced dimension ID at death. |
| `x`, `y`, `z` | `float` | Player position captured at death. |

**Example**

```python
from boxloom import watch_event

with watch_event() as events:
    for event in events:
        if event.type == "chat.message":
            print(f"<{event.player.username}> {event.message}")
        elif event.type == "player.death":
            print(event.player.username, event.dimension, event.x, event.y, event.z)

# A literal filter selects the yielded type without an additional branch:
with watch_event("player.death") as deaths:
    for death in deaths:
        print(death.x)  # Inferred as PlayerDeathEvent by mypy and Pyright.
```

`EventType` uses `Literal`, so editors can suggest valid strings and type checkers
reject misspellings such as `"player.deth"`. `event.type` narrows the `Event` union.
Overloads return `EventStream[ChatEvent]` for `"chat.message"` and
`EventStream[PlayerDeathEvent]` for `"player.death"`. These types are included in the
installed package through its `py.typed` marker.

This function also exists on `BoxloomClient`. Filtering happens in the SDK over
the same `GET /v1/events` connection; skipped events still advance the cursor.
Unknown event names are skipped for forward compatibility. `stream.ready` is
handled internally, while stream resets and errors raise SDK exceptions.
Only confirmed player deaths are emitted; mob deaths and successful totem saves
do not produce `player.death`. Death notifications work even when Minecraft's
death messages are hidden.

</Operation>

## `subscribe_event`

<Operation id="subscribe_event">

```python
subscribe_event(
    event_type: Optional[EventType] = None,
    *,
    callback: Callable[[Event], None],
    on_error: Optional[Callable[[Exception], None]] = None,
    last_event_id: Optional[str] = None,
    reconnect: bool = True,
) -> EventSubscription
```

**Parameters**

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `event_type` | `Optional[EventType]` | `None` | All supported types, `"chat.message"`, or `"player.death"`. Filtering happens in the SDK. |
| `callback` | `Callable[[Event], None]` | required | A synchronous callback. Overloads accept `Callable[[ChatEvent], None]` for `"chat.message"` and `Callable[[PlayerDeathEvent], None]` for `"player.death"`. |
| `on_error` | `Optional[Callable[[Exception], None]]` | `None` | Called once when background reception or a callback fails. Without it, the failure is logged. |
| `last_event_id` | `Optional[str]` | `None` | Resume strictly after this cursor; otherwise start at the live position. |
| `reconnect` | `bool` | `True` | Retry transient receive failures using the current cursor. Use `False` to treat a dropped connection as a game-ending error. |

**Returns** — `EventSubscription`, after the server has sent `stream.ready`.
Initial authentication, connection, readiness, and protocol failures are raised
synchronously. Each subscription owns its connection and a daemon thread. Its
callbacks run serially, in receive order, and may call other SDK operations.
Initialize shared game state before subscribing; callbacks can start before the
registration call returns. Prefer annotated `def` handlers for type checking;
coroutine callbacks are rejected.

| Member | Description |
| --- | --- |
| `stop()` | Request cooperative shutdown without waiting. Idempotent and safe inside a callback. |
| `join(timeout=None)` | Wait for the worker to finish. A finite timeout raises `TimeoutError` if it is still running. Joining from the callback thread raises `RuntimeError`. |
| `raise_if_failed()` | Re-raise a saved receive or callback failure on the calling thread. |
| `last_event_id` | Last successfully processed cursor, advanced after callbacks return or filtered-out events are skipped. |
| `with` | Request a stop and join on exit, then surface a background error unless the context already has an exception. |

**Example**

```python
from threading import Event as Signal
from boxloom import PlayerDeathEvent, subscribe_event

game_over = Signal()

def on_death(event: PlayerDeathEvent) -> None:
    if event.player.username == "Steve":
        game_over.set()

def on_error(error: Exception) -> None:
    print(f"Event monitoring failed: {error}")
    game_over.set()

with subscribe_event(
    "player.death", callback=on_death, on_error=on_error, reconnect=False,
) as subscription:
    while not game_over.wait(1.0):
        subscription.raise_if_failed()
        # Advance the game, e.g. summon TNT above the participant.
    subscription.raise_if_failed()
```

A long-running callback delays subsequent delivery. Use thread-safe signals or
locks when sharing state with the game loop. Stopping does not interrupt an
active callback or cancel Minecraft commands already sent; an idle network read
can take up to the configured client timeout to finish. Use a `with` block, or
call `stop()` and `join()` before releasing state used by callbacks.

Background failures stop the subscription and remain observable even when
`on_error` is supplied. A failing error handler is logged without replacing the
original failure. The failed event is not acknowledged and its callback is not
retried automatically. Reconnection reuses retained cursor history; an expired
cursor is a terminal error. Use idempotent side effects when persisting cursors
across process restarts.

</Operation>
