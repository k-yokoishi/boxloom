Every operation below is available through the boxloom Python SDK. The same operations are documented for the [REST API](./rest).

These examples use the connection configured during [Installation](../installation).

## Conventions

Top-level functions share one process-wide client. Call `boxloom.init()` to configure it explicitly, or let the first call configure it from `BOXLOOM_BASE_URL`, `BOXLOOM_AUTH_TOKEN`, and `BOXLOOM_TIMEOUT_SECONDS`.

Dimensions, blocks, and entities are named with namespaced IDs such as `minecraft:overworld`, `minecraft:stone`, and `minecraft:arrow`. A dimension must be loaded by the running server; a block or entity ID must exist in the server's registries. Operations that act on the world take `dimension` as a keyword argument defaulting to `minecraft:overworld`.

### Block, entity, and item constants

Use `blocks`, `entities`, and `items` to select vanilla IDs with editor completion:

```python
from boxloom import BlockPos, Vec3, blocks, entities, give_item, items, set_block, summon

set_block(BlockPos(0, 100, 0), blocks.DIAMOND_BLOCK)
summon(entities.PIG, Vec3(0, 101, 0))
give_item("Steve", items.BONE_MEAL, 3)
```

Type `blocks.`, `entities.`, or `items.` to browse names. These are ordinary strings, such as
`blocks.DIAMOND_BLOCK == "minecraft:diamond_block"`, annotated with `Final[str]`.
Block constants also work with `fill`; entity constants also work with
`kill_entities`. Item constants such as `items.BONE_MEAL`, `items.DIAMOND_SWORD`,
and `items.STONE` work with `give_item` and `Player.give_item`.
All `BoxloomClient` methods accept them as well.

Constants cover vanilla Minecraft 26.3 and are bundled with the SDK, so completion
works without connecting to a server. `blocks.MINECRAFT_VERSION` and
`entities.MINECRAFT_VERSION`, along with `items.MINECRAFT_VERSION`, expose their
source version. Namespaced strings remain
accepted, including IDs from installed Mods. The server validates availability and
summonability; some registered types, such as `entities.PLAYER`, cannot be summoned.
Likewise, `items.AIR` is registered but cannot be given.

### Coordinates and results

Use `Vec3(x, y, z)` for player/entity positions, directions, and offsets, and
`BlockPos(x, y, z)` for block positions. `Vec3` stores finite floats; `BlockPos`
requires signed 32-bit integers. Both reject booleans and are frozen dataclasses
with named `x`, `y`, and `z` components, equality, and hashing. Results are also
frozen dataclasses.

Both types support `a + b`, `a - b`, `-a`, `a * scale`, and `scale * a`.
Operands for addition/subtraction must have the same coordinate type; `Vec3`
accepts finite numeric scales, while `BlockPos` accepts only integer scales.
Arithmetic that produces non-finite or out-of-range components raises `ValueError`.

```python
from boxloom import BlockPos, Vec3, blocks, get_player_location, set_block, teleport_player

location = get_player_location("Steve")
teleport_player("Steve", location.position + Vec3(0, 10, 0))
origin = location.position.to_block_pos()
set_block(origin + BlockPos(1, -1, 0), blocks.DIAMOND_BLOCK, dimension=location.dimension)
```

`Vec3.to_block_pos()` uses floor on each component: `Vec3(-0.2, 64.8, 3.9)`
becomes `BlockPos(-1, 64, 3)`. `BlockPos.to_vec3()` returns the block's minimum
corner; add `Vec3(0.5, 0.5, 0.5)` to obtain its center. The two types are not
implicitly interchangeable. Neither contains a dimension; pass `dimension`
separately to world operations.

Every operation runs on the Minecraft server thread, so a stalled server surfaces as a timeout rather than a hang.

`get_block()` returns the immutable `Block` class. It holds `dimension`, `position` (`BlockPos`),
the namespaced block ID in `block`, and a read-only `properties` mapping.
`TargetedBlock` inherits from `Block`,
so functions that need this common information can accept either result:

```python
from boxloom import BlockPos, Block, get_block, get_player

def describe(block: Block) -> str:
    return f"{block.block} at ({block.position.x}, {block.position.y}, {block.position.z})"

print(describe(get_block(BlockPos(0, 64, 0))))
player = get_player("Steve")
if player is not None:
    target = player.get_targeted_block()
    if target is not None:
        print(describe(target))
```

`TargetedBlock` additionally carries the hit `face` and `distance`.

## Errors

Every failure raises a subclass of `boxloom.BoxloomError`.

| Exception | Raised when |
| --- | --- |
| `ApiError` | The server returned an error response. Carries `status`, `code`, and `message`. |
| `ConnectionError` | The boxloom server could not be reached. |
| `ProtocolError` | The response did not match the API contract. |
| `ConfigurationError` | The connection configuration is missing or invalid. |
| `EventCursorExpiredError` | An event stream cursor can no longer be resumed. Subclass of `ApiError`. |
| `EventStreamError` | The server reported a failure after the event stream was open. |

```python
from boxloom import BlockPos, ApiError, set_block

try:
    set_block(BlockPos(0, 100, 0), "minecraft:not_a_block")
except ApiError as error:
    print(error.status, error.code, error.message)
```

`ApiError.status` and `ApiError.code` carry the HTTP status and machine-readable code from the server. These can come from any operation; codes specific to one operation are listed with that operation.

## `Player` methods

Resolve a connected player with `get_player(username)`, also available as
`BoxloomClient.get_player(username)`:

```python
get_player(username: str) -> Optional[Player]
```

Returns `None` if the player is not connected. Invalid names raise `ValueError`;
connection, authentication and other API failures raise their usual exceptions.
This reads the existing position endpoint to resolve the player's identity.
Players returned by `get_players()` are also
actionable. Each retains its originating client, including after `boxloom.init()`
changes the process-wide configuration.

```python
from boxloom import get_player

player = get_player("Steve")
if player is None:
    raise RuntimeError("Steve is not connected")
target = player.get_targeted_block()
if target is not None:
    print(target.block, target.position.x, target.position.y, target.position.z, target.face)
result = player.attack()
print(result.swung, result.broken)
```

Players received through `watch_event()`, `watch_chat()`, and `subscribe_event()`
also retain the receiving client. You can call `event.player.get_location()` and
other player methods directly, including after `boxloom.init()` changes the
default client. Manually constructed `Player` values have no client binding;
calling their methods raises `ConfigurationError`. Resolve them with the
appropriate client's `get_player(username)` first.

### `Player.get_location`

```python
player.get_location() -> PlayerLocation
```

Read the player's latest position, dimension, and look direction through its
originating client. Each call requests a fresh snapshot from the server.
Returns the same [`PlayerLocation`](#get_player_location) as
`get_player_location(player.username)`, including `position` (`Vec3`),
`dimension`, `yaw`, and `pitch`.

```python
location = player.get_location()
print(location.position.x, location.position.y, location.position.z)
print(location.position.to_block_pos())
```

### `Player.get_targeted_block`

<Operation id="get_targeted_block">


| Attribute | Type | Description |
| --- | --- | --- |
| `dimension` | `str` | The player's dimension. |
| `position` | `BlockPos` | Absolute block coordinates. |

### `Player.attack`

<Operation id="attack">

```python
player.attack() -> PlayerAttackResult
```

Also available as `BoxloomClient.attack_player(username)`.

| Attribute | Type | Description |
| --- | --- | --- |
| `swung` | `bool` | Whether a new arm swing started. An existing swing may prevent another. |
| `target` | `Optional[TargetedBlock]` | Block snapshot captured before the attack; `None` for entity attacks and misses. |
| `broken` | `bool` | Whether the targeted block's type changed during the attack. |
| `entity` | `Optional[Entity]` | Entity snapshot after an entity attack attempt; `None` for block attacks and misses. Damage is not guaranteed. |

This is a single click: survival blocks that require sustained mining remain in
place. Creative and instant-mine blocks can break. A targeted block may remain
because of protection rules, the held tool, or cancellation by another mod.
An entity within native attack reach can be attacked, with normal damage cooldowns,
PvP rules and Fabric cancellation. Blocks and entities use their own reach values;
a wall blocks attacks on entities behind it. Piercing weapons are rejected with
`UNSUPPORTED_ATTACK_TARGET`. Calling `attack()` cancels any API mining session.
This operation is not retried automatically; a
timeout can occur after the action has already taken effect.

</Operation>

### `Player.use`

<Operation id="use">

```python
player.use() -> PlayerUseResult
```

Also available as `BoxloomClient.use_player_item(username)`.

Hold bone meal in your main hand and aim at a growing plant before running:

```python
from boxloom import get_player

player = get_player("Steve")
if player is None:
    raise RuntimeError("Steve is not connected")
result = player.use()
print(result.used, result.target)
```

| Attribute | Type | Description |
| --- | --- | --- |
| `used` | `bool` | Whether Minecraft accepted the action. This does not guarantee growth or item consumption. |
| `swung` | `bool` | Whether a new interaction arm swing started. |
| `target` | `Optional[TargetedBlock]` | Block snapshot before the attempt, or `None` for entities and air. |
| `entity` | `Optional[Entity]` | Entity snapshot after the attempt, including a refused attempt; `None` for blocks and air. |

Uses the latest server-side view and native block/entity interaction reach.
The main hand can apply bone meal, place blocks, operate a lever with an empty
hand, feed animals, or use items in the air. There is no automatic offhand fallback.
Intervening entities and blocks occlude targets. Fluids are ignored by the outer
raycast; items such as buckets use their own native targeting. Survival consumption,
creative rules, cooldowns, spawn protection and mod cancellation apply. Refused or
ineffective uses return `used=False`; dead, spectator or already-using players
raise `409 PLAYER_CANNOT_USE`.

A block that does not handle the interaction may fall back to in-air item use;
`target` still describes that block. A cancelled interaction stops without this
fallback. API block/item uses emit the existing `block.use` / `item.use` attempt
events; an interaction swing does not emit the attack-only `player.swing` event.

Calling `use()` cancels API mining and any API-owned continuous item use without
release effects. Long-duration items start native use, but a vanilla client can
immediately interrupt them. Use `start_using_item()` and `stop_using_item()` for
controlled eating, drinking or charging. Requests are not retried automatically: a timeout
can occur after the action has taken effect.

</Operation>

### `Player.start_using_item`

<Operation id="start_using_item">

```python
player.start_using_item() -> PlayerItemUseResult
```

Also available as `BoxloomClient.start_using_player_item(username)`.

Hold food in your main hand while hungry, then call:

```python
player = get_player("Steve")
if player is None:
    raise RuntimeError("Steve is not connected")
result = player.start_using_item()  # Returns immediately; one item finishes natively.
print(result.active, result.item, result.remaining_ticks)
```

| Attribute | Type | Description |
| --- | --- | --- |
| `active` | `bool` | Whether API-owned native use is active at response time. |
| `item` | `Optional[str]` | Namespaced item ID while active; `None` when inactive. |
| `remaining_ticks` | `int` | Nonnegative native use ticks remaining. Zero when inactive. This is a snapshot, not charge percentage. |

Uses the main-hand item itself, even while aiming at an interactive block; it does
not operate that block or an entity. Empty hands and instant-use items (bone meal,
blocks, ender pearls) return `409 ITEM_NOT_CONTINUOUSLY_USABLE` before use. Normal
food at full hunger, cooldowns and mod cancellation return an inactive result.
An existing use started in the Minecraft client returns `409 PLAYER_CANNOT_USE`.

While this API owns the use, client `RELEASE_USE_ITEM` packets are ignored, including
the automatic release sent when the physical use key is not held. Other client use
is unchanged. No client mod is required. A vanilla client can stop its local
first-person animation even while the server continues consumption or charging.

Food/drink finishes one item and ends automatically. Holding a bow or shield
continues until release. Slot or held-stack changes, world or game-mode changes,
death, disconnect, server shutdown, API attack, `use()` or mining start cancel
without release effects; these cancellations never fire a bow. Starting item use
cancels API mining. Repeating start while active preserves progress, but calling
start after completion begins another use; do not use start to poll for completion.

</Operation>

### `Player.stop_using_item`

<Operation id="stop_using_item">

```python
player.stop_using_item() -> PlayerItemUseResult
```

Also available as `BoxloomClient.stop_using_player_item(username)`.

This is a use-button release. Food/drink is interrupted without consumption; a
charged bow fires with native ammo and durability rules. It always returns
`active=False`, `item=None` and `remaining_ticks=0`. Stopping an inactive,
completed or invalidated API session is idempotent and leaves client-owned use
alone. Both operations are mutations and are not retried automatically.

```python
import time

player.start_using_item()  # Hold a bow with arrows available.
try:
    time.sleep(1)
finally:
    player.stop_using_item()  # Release the bow.
```

</Operation>

### `Player.start_mining`

<Operation id="start_mining">

```python
player.start_mining() -> PlayerMiningResult
```

Also available as `BoxloomClient.start_player_mining(username)`.

| Attribute | Type | Description |
| --- | --- | --- |
| `active` | `bool` | Whether held mining is enabled, including while waiting without a target. |
| `target` | `Optional[TargetedBlock]` | Current block snapshot, or the block immediately broken by this request; `None` while waiting without a target. |
| `broken` | `bool` | Whether this request immediately broke the block, as in creative or instant mining. |

This acts like holding the mining button. It returns immediately with `active=True`,
even when no block is targeted. The server waits for a block under the crosshair,
mines it and continues to the next block after a five-tick break delay. An immediate
creative or instant break returns both `active=True` and `broken=True`.

Looking away cancels that block's progress and waits for a target. A new target,
block state, held stack or selected slot starts fresh progress. Item use pauses
mining. Protected and unbreakable targets stay intact; mining waits for the aim,
block or tool to change. This operation only mines blocks and does not attack
entities. The player receives arm swings and crack progress as well as observers.

Call `stop_mining()` to release the hold. `attack()`, `use()`, `start_using_item()`,
a different slot selected through `select_slot()`, death, disconnect, world or
game-mode changes, and a competing native mining action also end the mode.

```python
import time
from boxloom import get_player

player = get_player("Steve")
if player is None:
    raise RuntimeError("Steve is not connected")
player.start_mining()  # No targeted block is required.
try:
    time.sleep(10)  # Aim at blocks during this time to mine them continuously.
finally:
    player.stop_mining()
```

The tool and block determine the required time. `active` and `broken` are snapshots
at request time; read blocks to observe later breaks.

</Operation>

### `Player.stop_mining`

<Operation id="stop_mining">

```python
player.stop_mining() -> PlayerMiningResult
```

Also available as `BoxloomClient.stop_player_mining(username)`. Returns `active=False`
and `broken=False`. `target` is the current block snapshot, or `None` while waiting
without a target or already inactive. It is safe to call from `finally`.

</Operation>

## `give_item`

<Operation id="give_item">

```python
give_item(username: str, item: str, count: int = 1) -> GiveItemResult
BoxloomClient.give_item(username: str, item: str, count: int = 1) -> GiveItemResult
Player.give_item(item: str, count: int = 1) -> GiveItemResult
```

**Parameters**

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `username` | `str` | required | Connected player name; supplied by the bound `Player` for its method. |
| `item` | `str` | required | Registered item ID, such as `"minecraft:stone"` or `"minecraft:diamond_sword"`. The `minecraft:` prefix may be omitted. |
| `count` | `int` | `1` | Positive integer, at most 100 stacks of this item: 6,400 stone, 1,600 snowballs, or 100 swords. |

Use `items.STONE`, `items.BONE_MEAL`, or `items.DIAMOND_SWORD` for editor completion.
`blocks.STONE` can also be passed because its value is a valid item ID. World-only
blocks such as water have no item form. Registered mod item IDs are accepted.
Components and NBT are not accepted. Invalid argument types raise `ValueError`
before requesting; item existence and the item-specific count limit are checked
on the server. Requests are not retried automatically.

**Returns** — `GiveItemResult`

| Attribute | Type | Description |
| --- | --- | --- |
| `username` | `str` | The player's name. |
| `uuid` | `str` | The player's UUID. |
| `item` | `str` | Canonical namespaced item ID. |
| `count` | `int` | Requested amount given, including overflow handled by vanilla rules. |
| `slot` | `int \| None` | Lowest hotbar index that received items; `None` if none did. |
| `slots` | `tuple[GivenItemSlot, ...]` | All destinations, ordered by slot index. Each entry has `slot: int` and `count: int` (the added count, not the final stack size). |

Inventory indices are `0–8` for the hotbar, `9–35` for the main inventory, and
`40` for the offhand. Dropped or discarded overflow has no destination slot.
The result is a snapshot: later player actions may move or consume the items.

```python
from boxloom import get_player, give_item, items

player = get_player("Steve")
if player is not None:
    player.give_item(items.STONE, count=64)
    player.give_item(items.DIAMOND_SWORD)

result = give_item("Steve", items.BONE_MEAL, count=16)
print(result.item, result.count)
```

To connect giving, selecting, and using bone meal, leave a hotbar slot empty and
aim at a growing plant in Minecraft:

```python
player = get_player("Steve")
if player is not None:
    result = player.give_item(items.BONE_MEAL, 16)
    if result.slot is not None:
        player.select_slot(result.slot)
        player.use()
```

If `slot` is `None`, check `slots`: items may have gone into the main inventory
or offhand, or overflowed. Move them into the hotbar in Minecraft before use.

</Operation>

## `set_block`

<Operation id="set_block">

```python
set_block(
    position: BlockPos,
    block: str,
    *,
    dimension: str = "minecraft:overworld",
    properties: Optional[Mapping[str, str]] = None,
) -> SetBlockResult
```

**Parameters**

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `position` | `BlockPos` | required | Block coordinates, within the 32-bit integer range. |
| `block` | `str` | required | Namespaced ID of a registered block. |
| `properties` | `Optional[Mapping[str, str]]` | `None` | Overrides applied to the block default state. All keys and values must be non-empty strings. |
| `dimension` | `str` | `"minecraft:overworld"` | Namespaced ID of a loaded dimension. |

**Returns** — `SetBlockResult`

| Attribute | Type | Description |
| --- | --- | --- |
| `changed` | `bool` | Whether the world changed, including a property-only change. `False` for an identical state or a position outside build height. |
| `dimension` | `str` | Resolved namespaced dimension ID. |
| `position` | `BlockPos` | The requested block coordinates. |
| `block` | `str` | Namespaced ID of the actual block after the attempt. |
| `properties` | `Mapping[str, str]` | Read-only map of the complete state after the attempt, including unchanged positions. |

**Example**

```python
from boxloom import BlockPos, blocks, set_block

result = set_block(BlockPos(0, 100, 0), blocks.DIAMOND_BLOCK)
print(result.changed, result.properties)

# Plant wheat at growth stage 3, on farmland.
set_block(BlockPos(0, 99, 0), blocks.FARMLAND, properties={"moisture": "7"})
result = set_block(BlockPos(0, 100, 0), blocks.WHEAT, properties={"age": "3"})
print(result.properties)  # {"age": "3"}
```

`properties=None` or `{}` uses the block default state. Properties are not merged
with the previous block: setting wheat without `age` resets it to age `0`.
Use string values such as `"3"` and `"true"`, including for numbers and booleans.
Unknown property names or invalid values return `400 INVALID_BLOCK_PROPERTY`
before any world change. Property value ranges depend on the block.

The response reads the actual state after the attempt; it may differ from the
requested state after neighbor updates or an unsuccessful placement. An older
server that omits `properties` is read as an empty mapping by the SDK.

</Operation>

```python
fill(start, end, blocks.AIR, mode="destroy", replace=blocks.STONE)

```

| Mode | Behavior |
| --- | --- |
| `"replace"` | Set all matching positions without breaking the original blocks. |
| `"destroy"` | Break matching blocks with native drops before placing the destination. |
| `"keep"` | Set only air. Cannot be combined with `replace`. |

player's held tool or enchantments. A destroyed position counts even if the
destination is air or the same block type; the result is not an item count.
No-op fills succeed with zero. The size limit applies before filtering.

## `watch_event`

<Operation id="watch_event">

```python
EventType = Literal[
    "chat.message", "player.death", "player.swing", "block.attack", "block.use", "item.use",
]
Event = Union[
    ChatEvent, PlayerDeathEvent, PlayerSwingEvent, BlockAttackEvent, BlockUseEvent, ItemUseEvent,
]

watch_event(
    event_type: Optional[EventType] = None,
    *,
    last_event_id: Optional[str] = None,
    reconnect: bool = True,
) -> EventStream[Event]
```

Import `events` from `boxloom` to use named event filters. These constants work
with `watch_event()`, `subscribe_event()`, and comparisons against `event.type`.
They preserve the corresponding event type in mypy and Pyright. String filters
are also supported.

| Constant | Event name | Event class |
| --- | --- | --- |
| `events.CHAT_MESSAGE` | `"chat.message"` | `ChatEvent` |
| `events.PLAYER_DEATH` | `"player.death"` | `PlayerDeathEvent` |
| `events.PLAYER_SWING` | `"player.swing"` | `PlayerSwingEvent` |
| `events.BLOCK_ATTACK` | `"block.attack"` | `BlockAttackEvent` |
| `events.BLOCK_USE` | `"block.use"` | `BlockUseEvent` |
| `events.ITEM_USE` | `"item.use"` | `ItemUseEvent` |

```python
from boxloom import events, watch_event

with watch_event(events.CHAT_MESSAGE) as chats:
    for chat in chats:  # Inferred as ChatEvent.
        print(chat.player.username, chat.message)
```

**Parameters**

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `event_type` | `Optional[EventType]` | `None` | Receive all supported event types, or filter to one `EventType`. Unknown values raise `ValueError`. |
| `last_event_id` | `Optional[str]` | `None` | Resume strictly after this event ID. `None` starts at the live position when iteration first opens the connection. |
| `reconnect` | `bool` | `True` | Reconnect automatically using the last received cursor after a connection drops. |

**Returns** — `EventStream[Event]`, an iterator and context manager with `last_event_id` and `close()`.

The stream yields the six event classes listed above. All carry:

| Attribute | Type | Description |
| --- | --- | --- |
| `type` | `EventType` | Fixed event discriminator matching the selected `EventType`. |
| `id` | `str` | Opaque event ID, usable as `last_event_id`. |
| `timestamp` | `str` | UTC ISO-8601 instant. |
| `player` | `Player` | The player, with `username` and `uuid`. |

`ChatEvent` and `PlayerDeathEvent` also carry `message` (`str`), the chat text
or Minecraft's plain-text death message. `PlayerDeathEvent` also carries:

| Attribute | Type | Description |
| --- | --- | --- |
| `dimension` | `str` | Namespaced dimension ID at death. |
| `position` | `Vec3` | Player position captured at death. |

**Player action events**

| Filter | Yielded class | Meaning |
| --- | --- | --- |
| `"player.swing"` | `PlayerSwingEvent` | An attack arm swing, including misses. |
| `"block.attack"` | `BlockAttackEvent` | A request to start attacking a block. |
| `"block.use"` | `BlockUseEvent` | A request to use a block. |
| `"item.use"` | `ItemUseEvent` | A request to use a non-empty held item. |

All four carry `dimension` (`str`), player `position` (`Vec3`),
`hand` (`Literal["main_hand", "off_hand"]`), and `item` (`Optional[str]`,
a namespaced item ID or `None` for an empty hand). Block events additionally
carry `block` (`str`), `block_position` (`BlockPos`, target coordinates),
and `face` (`"down"`, `"up"`, `"north"`, `"south"`, `"west"`, or `"east"`).
Values are captured on the server thread before consumption or other changes.
Action events have no `message` field.

These are attempts, not confirmations of success. Swings include attacks that
hit, miss, or target blocks, and do not identify their target. One operation can
emit both `player.swing` and `block.attack`. Holding a button can repeat events.
In Minecraft 26.3 swings use the main hand. Item use on a block (such as placement)
is observed as `block.use`; `item.use` observes the separate item-use path.
Spectator actions are excluded. No client mod is required.

```python
from boxloom import events, watch_event

with watch_event(events.PLAYER_SWING) as swings:
    for event in swings:  # Inferred as PlayerSwingEvent.
        if event.item == "minecraft:diamond_sword":
            print(event.player.username, "swung a diamond sword")
```

**Example**

```python
from boxloom import events, watch_event

with watch_event() as stream:
    for event in stream:
        if event.type == events.CHAT_MESSAGE:
            print(f"<{event.player.username}> {event.message}")
        elif event.type == events.PLAYER_DEATH:
            print(event.player.username, event.dimension, event.position.x, event.position.y, event.position.z)

# A named filter selects the yielded type without an additional branch:
with watch_event(events.PLAYER_DEATH) as deaths:
    for death in deaths:
        print(death.position.x)  # Inferred as PlayerDeathEvent by mypy and Pyright.
```

`EventType` uses `Literal`, so editors can suggest valid strings and type checkers
reject misspellings such as `"player.deth"`. `event.type` narrows the `Event` union.
Overloads return `EventStream[ChatEvent]` for `"chat.message"` and
`EventStream[PlayerDeathEvent]` for `"player.death"`, with equivalent overloads for
each action event. These types are included in the
installed package through its `py.typed` marker.

`event.player.get_location()` reads a fresh `PlayerLocation` through the stream's
original client. Its `.position` is a `Vec3` and its `.dimension` identifies the
player's current world. Death and action events' own `position` and `dimension`
fields remain snapshots from when the event occurred.

This function also exists on `BoxloomClient`. Filtering happens in the SDK over
the same `GET /v1/events` connection; skipped events still advance the cursor.
Unknown event names are skipped for forward compatibility. `stream.ready` is
handled internally, while stream resets and errors raise SDK exceptions.
Only confirmed player deaths are emitted; mob deaths and successful totem saves
do not produce `player.death`. Death notifications work even when Minecraft's
death messages are hidden.

</Operation>

## `subscribe_event`

<Operation id="subscribe_event">

```python
subscribe_event(
    event_type: Optional[EventType] = None,
    *,
    callback: Callable[[Event], None],
    on_error: Optional[Callable[[Exception], None]] = None,
    last_event_id: Optional[str] = None,
    reconnect: bool = True,
) -> EventSubscription
```

**Parameters**

| Name | Type | Default | Description |
| --- | --- | --- | --- |
| `event_type` | `Optional[EventType]` | `None` | All supported types, or one `EventType`. Filtering happens in the SDK. |
| `callback` | `Callable[[Event], None]` | required | A synchronous callback. Overloads select the corresponding event class, e.g. `Callable[[PlayerSwingEvent], None]` for `"player.swing"`. |
| `on_error` | `Optional[Callable[[Exception], None]]` | `None` | Called once when background reception or a callback fails. Without it, the failure is logged. |
| `last_event_id` | `Optional[str]` | `None` | Resume strictly after this cursor; otherwise start at the live position. |
| `reconnect` | `bool` | `True` | Retry transient receive failures using the current cursor. Use `False` to treat a dropped connection as a game-ending error. |

**Returns** — `EventSubscription`, after the server has sent `stream.ready`.
Initial authentication, connection, readiness, and protocol failures are raised
synchronously. Each subscription owns its connection and a daemon thread. Its
callbacks run serially, in receive order, and may call other SDK operations.
Initialize shared game state before subscribing; callbacks can start before the
registration call returns. Prefer annotated `def` handlers for type checking;
coroutine callbacks are rejected.

| Member | Description |
| --- | --- |
| `stop()` | Request cooperative shutdown without waiting. Idempotent and safe inside a callback. |
| `join(timeout=None)` | Wait for the worker to finish. A finite timeout raises `TimeoutError` if it is still running. Joining from the callback thread raises `RuntimeError`. |
| `raise_if_failed()` | Re-raise a saved receive or callback failure on the calling thread. |
| `last_event_id` | Last successfully processed cursor, advanced after callbacks return or filtered-out events are skipped. |
| `with` | Request a stop and join on exit, then surface a background error unless the context already has an exception. |

**Example**

```python
from threading import Event as Signal
from boxloom import PlayerDeathEvent, events, subscribe_event

game_over = Signal()

def on_death(event: PlayerDeathEvent) -> None:
    if event.player.username == "Steve":
        game_over.set()

def on_error(error: Exception) -> None:
    print(f"Event monitoring failed: {error}")
    game_over.set()

with subscribe_event(
    events.PLAYER_DEATH, callback=on_death, on_error=on_error, reconnect=False,
) as subscription:
    while not game_over.wait(1.0):
        subscription.raise_if_failed()
        # Advance the game, e.g. summon TNT above the participant.
    subscription.raise_if_failed()
```

A long-running callback delays subsequent delivery. Use thread-safe signals or
locks when sharing state with the game loop. Stopping does not interrupt an
active callback or cancel Minecraft commands already sent; an idle network read
can take up to the configured client timeout to finish. Use a `with` block, or
call `stop()` and `join()` before releasing state used by callbacks.

Background failures stop the subscription and remain observable even when
`on_error` is supplied. A failing error handler is logged without replacing the
original failure. The failed event is not acknowledged and its callback is not
retried automatically. Reconnection reuses retained cursor history; an expired
cursor is a terminal error. Use idempotent side effects when persisting cursors
across process restarts.

</Operation>
